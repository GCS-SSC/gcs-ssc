# Applicant Recipient Authorization

The `Applicant Recipient` module uses the `applicant_recipient` subject in RBAC.

## Required Ability

All profile and team access starts with the matching `applicant_recipient` ability:

- `create`
- `read`
- `update`
- `delete`

Without the required ability, access is denied even if the user belongs to the right Agency or is on the Team.

## Profile Authorization Rules

### Read

- Requires `applicant_recipient:read`
- Not scoped by Agency

A user with the `read` ability can list and open Applicant Recipient Profiles across agencies.

### Create

- Requires `applicant_recipient:create`
- Scoped to the selected Lead Agency
- Lead Agency is required on create

A user can create an Applicant Recipient Profile only when they hold an `applicant_recipient:create` grant that covers the selected Lead Agency. The selected subtype must still belong to that same Lead Agency.

### Update

- Requires `applicant_recipient:update`
- Scoped to the profile's current Lead Agency, unless the user is on that profile's Team

A user can update an Applicant Recipient Profile when at least one of the following is true:

1. They are a root administrator.
2. The profile has no Lead Agency.
3. They hold an `applicant_recipient:update` grant that covers the profile's current Lead Agency.
4. They are listed in the `Applicant Recipient Team` table for that profile.

Team membership is an edit fallback. It does not replace the base `update` ability.

### Lead Agency Reassignment

Changing the Lead Agency is stricter than a normal update.

The user must:

- already be allowed to update the existing profile
- and also hold an `applicant_recipient:update` scoped grant for the next Lead Agency

Team membership alone is not enough to move a profile to a different Lead Agency.

### Delete

- Requires `applicant_recipient:delete`
- Scoped to the profile's current Lead Agency, unless the user is on that profile's Team

Delete is allowed when at least one of the following is true:

1. They are a root administrator.
2. The profile has no Lead Agency.
3. They hold an `applicant_recipient:delete` grant that covers the profile's current Lead Agency.
4. They are listed in the `Applicant Recipient Team` table for that profile.

Delete is implemented as soft deletion by setting `_deleted = true`.

## Applicant Recipient Team Authorization Rules

The Team table controls which users may also edit the profile.

### Team List / Create / Update

These Team routes use the profile update gate:

- the user must have `applicant_recipient:update`
- and they must already be allowed to update that profile

That means Team management is allowed when the user:

- has a Lead-Agency-scoped `update` grant for the profile
- or is already on the profile Team
- or is root admin

### Team Delete

Deleting a Team assignment is stricter:

- the user must have `applicant_recipient:delete`
- and they must already be allowed to delete that profile

That means Team assignment deletion is allowed when the user:

- has a Lead-Agency-scoped `delete` grant for the profile
- or is already on the profile Team
- or is root admin

## Agency Financial ID Authorization Rules

Agency Financial IDs are still managed with unscoped applicant-recipient child-record permissions:

- `read` requires `applicant_recipient:read`
- `create` requires `applicant_recipient:create`
- `update` requires `applicant_recipient:update`
- `delete` requires `applicant_recipient:delete`

Unlike the parent profile, these child routes do not require the Applicant Recipient Profile's Lead Agency to match the caller's scope.

The linked `Agency` field is stricter:

- on create, the selected Agency must be covered by the caller's `applicant_recipient:create` scoped grant, unless the caller has global access
- on update, the resulting Agency must be covered by the caller's `applicant_recipient:update` scoped grant, unless the caller has global access
- the Agency dropdown only lists Agencies covered by the matching scoped grant for the current action

This means a user may have unscoped permission to manage Agency Financial ID rows in general, but they still cannot attach a row to an Agency outside the Agencies covered by that user's roles.

## UI Flags

The profile detail and profile list responses expose:

- `can_update`
- `can_delete`
- `can_manage_team`
- `can_manage_team_update`
- `can_manage_team_delete`

These flags resolve as follows:

- `can_update`: `true` when the user can update the profile
- `can_delete`: `true` when the user can delete the profile
- `can_manage_team`: mirrors Team-tab visibility and currently follows `can_manage_team_update`
- `can_manage_team_update`: `true` when Team add/list/edit is allowed
- `can_manage_team_delete`: `true` when Team member deletion is allowed

## Practical Examples

- An agency-scoped user with `applicant_recipient:read` can open profiles from other agencies.
- An agency-scoped user with `applicant_recipient:create` can only create a profile for a Lead Agency covered by that user's create grant.
- That same user cannot edit a profile owned by another Lead Agency unless they are added to its Team.
- Once added to the Team, that user can edit the profile provided they still have `applicant_recipient:update`.
- That same Team member can delete the profile or remove Team members only if they also have `applicant_recipient:delete`.
- A Team member still cannot reassign the profile to a new Lead Agency unless their scoped grant also covers the new agency.
