# Additional Reviewers

Additional Reviewers are runtime work items attached to an executable runtime entity. For runtime reviews, that executable entity is `commonreview`.

## How It Works

An Additional Reviewer row does not create a new permission model. The row is stored against the executable runtime entity, but access still resolves through the parent business entity that owns that runtime work.

For example:

- an assessment review is stored as a `commonreview`
- that review belongs to a review set
- that review set belongs to a parent entity such as an Applicant Recipient
- Additional Reviewer access is authorized through that parent entity, using the same runtime resolution pattern already used for reviews and assessments

This is important because the same pattern can later be reused for other executable entities such as funding case monitoring without inventing a separate RBAC subject for each runtime activity.

## RBAC Pattern

Current behavior for Additional Reviewers follows these rules:

- `Read`: anyone who can read the executable activity page can read Additional Reviewer rows
- `Create`: anyone who can update or execute the executable activity page can create a new row
- `Update`: only the user assigned to that specific row can update it
- `Complete`: only the user assigned to that specific row can complete it
- `Delete`: anyone who can update the executable activity page can delete it today

Assignment does **not** grant extra access. A user must already be able to open the executable activity through the normal parent-entity runtime authorization path.

## Assessment Example

Today the implemented UI host is the assessment page.

That means:

- reading the assessment allows reading its Additional Reviewer rows
- editing the assessment allows creating Additional Reviewer rows
- only the assigned user can edit or complete their row
- users with assessment update access can delete a row

The row itself is stored against `commonreview + reviewId`, but the system still resolves authorization through the parent entity behind that review.

## Reassignment And Completion

Additional Reviewer rows are intended to behave like a lightweight log of review work:

- new rows start incomplete
- completing a row records completion
- reassigning a row clears the recorded completion
- there is no reopen flow
- if more review work is needed later, create another row

## Future Activities

When a future executable entity adopts Additional Reviewers:

1. attach the row to the executable runtime entity
2. resolve authorization through the parent business entity
3. keep assigned-user ownership local to the row update and complete actions
4. do not invent a new standalone RBAC subject unless product requirements actually demand it
